# KhiCAS 二维预览候选（2026-11-17）

本轮是在用户已确认可用的 `mapped-cas-20261116` / RC1 上加入显示功能。
RC1 文件保持原样；本轮最终发行文件及验证状态见本目录 `VALIDATION.json`。
**RC1 的实机通过不自动代表本候选已经通过实机。**

最终配对文件为 `KhiMap.g1a` **9,860 B** 和 `KHICAS.BIN` **2,867,576 B**，
安装二进制合计 **2,877,436 B**，比 RC1 增加 **8,320 B**。两文件必须一起替换。
数学映像原始内容增量为 8,340 B，其中二维 UI 控制组增加 6,952 B，组合内核修补再增加 1,388 B；
启动器因常量变化减少 20 B。没有切除 C++ 异常表来实现这个体积。

## 装载突破的实际含义

OS 首先识别一个不到 10 KB 的 G1A。大程序、只读数据和 C++ 异常表放在
`KHICAS.BIN` 的 Flash 文件中。启动器校验文件长度和 SHA-256，建立文件页与
Flash 物理页的对应表，再由常驻 RAM 的缺页处理程序补充处理器地址映射。
处理器按映射直接读取 Flash；没有把约 2.86 MB 的文件全部搬到 RAM。

原 OS 路径的 512 个 4 KiB 页对应 **2,097,152 B（2 MiB）**，不能写成
2,000,000 B。用户提供的原版大小 2,094,444 B 在这个范围内。RC1 的 699 页和
本候选的 701 页由自有映射处理，未扩写原 OS 的 512 项表。

这解决的是原装载路径的程序映射容量，**没有增加物理 RAM，也没有增加存储器总容量**。
CAS 物理池仍为 32,768 B，跟踪上限仍为 24,576 B。启动器常驻块另占 OS 堆；
屏幕排版工作区位于静态应用 RAM，不从 CAS 池分配。完整新版桌面内核仍不能
仅凭此办法装入设备总存储空间，也不能假定大规模符号运算不再内存不足。

## 用户可见改动

- 标题显示 `KhiCAS`，去除 BASE02/MAPCAS 等试验代号。
- 输入默认附带二维预览，原有按键和文字编辑行保持可编辑；它不是另一个 CAS 求值器。
- F6 Options 中可切换 `Input 2D` 和 `Output`。开关在本次运行中有效，重新启动恢复默认开启。
- 输出默认优先二维显示：分式、根号、幂、括号和普通函数支持排版；矩阵暂以括号行文保留。
- 结果超出小预览尺寸时自动打开完整查看器；输入可按 F3 查看。结果有图形时 F3 仍优先进入图形。
- 完整二维查看器：方向键横纵滚动；SHIFT 加方向键大步滚动；EXE 回到左上；F1 切换文本；EXIT/F3 返回。
- 四个方向的箭头指出还有内容。不能安全排版的语法、未完成输入、复杂度超限均保留原文，文本查看器可以翻页到末尾。

这里解决显示裁剪，不把有限内存变为无限。输入原有 96 B 缓冲和结果 1,024 B
缓冲没有放大；原内核超过结果容量仍明确报错，而不是宣称能展示任意长计算结果。

## 数学内核范围

发行候选以 RC1 的完整静态计算器 Giac 归档为基础：

`1b127e8f3e44cdb7452ea5d8bad8e792d1a6ea4bfa6962a14910d2598028e098`

39 个数学单元、709 条注册命令，旧计算器分支与既有内存修补；不是桌面 Giac 2.1
全量移植，不含 Python。没有为加入排版删去原有代数、微积分或绘图函数。

最终组合归档 SHA-256：
`c9e9a3afc0b40c80239b57777b396fcc1d3c0b3a5286a6708e525d2d2ab822cc`。
39 个成员仅 `ksym2poly.o` 和 `kintgab.o` 改动，命令表不变。

本轮修复两处问题：Heaviside 求导后分布积分漏算线性变量的缩放；三个 r2sym
容器路径在扩容抛错时，裸指针尚无拥有者而泄漏。SH 中的 31 B 残留经原核心
控制组和宿主 LSan 栈交叉确认，修复是补齐所有权，不改变该转换的数学算法。
早期只有积分缩放修补的候选未通过恢复检查，未发布；组合生命周期修补后，
同一 SH ELF 通过 26 项定向数学/边界用例、1,422 个分配失败点和 6 次取消。
变量、Ans 和内存计费保持，下一次算术可用，最终关闭父池归零。
源码、早期失败和最终通过证据均在 `kernel/`；这不是所有 Giac 路径的 OOM 安全证明。

Lambert W 可以作为独立增补研究，不能直接照搬新版实现；需要主值/负一分支、
分支点附近精度、残差和低内存测试。本轮没有把它标记为已支持。

## 内存与构建

`src/math_layout.c/.h` 是只用于显示的 C 解析器，128 节点，12 层深度，SH 工作区
2,328 B，既不分配堆，也不调用 CAS。UI 新状态及对齐使静态 RAM 尾端从
`0x081010c0` 变为 `0x081019f0`，增加 2,352 B；保留原有栈/运行时保护区。

原工具链在任务 VM 中重链接完整程序。不能将 Windows GCC 与旧 Linux slim-LTO
归档混用。小启动器由原 Windows SDK 构建，未改变 SDK 或模拟器安装。

可复现入口：

1. `tools/stage.py` 冻结当前 UI、运行时、头文件和测试源，生成 `evidence/source.tar.gz` 和源哈希清单。
2. `audit/build-env-20261114/vm.py extract` 送入原 VM；`tools/build_payload.py --compile-only` 可先检查小对象。
3. 同一脚本 `--run` 进行一次串行完整 LTO。最终版明确传入 `--core /root/khicas-work/preview-kernel-20261117/kernel/build-v3/libgiac-kernel-preview.a` 及上面的组合 `--core-sha`，输出到 `payload-final-build`。默认原核只用于显示控制组，不能混淆。
4. 回收 `payload-final-build.tar.gz`；`loader/tools/prepare_image.py payload-final-build/payload.bin bundle` 生成 BIN 和对应启动器校验头。
5. SDK 先 Debug 后 Release 构建 `loader/`，将 Release 的 G1A 命名为 `KhiMap.g1a` 放入 bundle。
6. 使用 `tools/run_session.py` 正常启动这两个最终文件。`tools/send_keys.py` 只发送按键和观察屏幕，不注入程序或改写目标内存。

新 BIN 必须配套重建的 G1A；严禁混用 RC1/本候选两个文件。回退时也要成对替换。
